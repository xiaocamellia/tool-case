# 《坐标系账本设计方案》需求论证意见

| 项目 | 内容 |
|---|---|
| 论证对象 | 坐标系账本（Coordinate Ledger）设计方案 v1.0（2026-11-12） |
| 论证性质 | 需求面向论证（不涉及代码实现评审） |
| 论证视角 | 分系统设计师，产品设计与验证阶段 |
| 论证依据 | 方案全文 + 便携工具箱现有工程结构 |
| 结论 | **方向正确，需求覆盖不完整，建议补 3 类需求并重排最小闭环后再开发** |

---

## 1. 论证范围与方法

本次论证只回答一个问题：**方案提出的功能，是否足以支撑"坐标系定义、转换、复核"这三件设计师真正每天在做的事。**

方法是三条追溯链：

1. **痛点 → 功能**：方案 1.1 节列了 5 条痛点，逐条核对是否有功能闭环；
2. **场景 → 用例**：方案 3.3 节列了 5 个典型场景（A~E），逐个核对是否有用例与功能承接；
3. **用户原话 → 范围边界**：设计者口述需求是"定义、转换、**复核**都很麻烦"，核对 1.3 节"不是什么"是否把复核排除在外。

架构分层、数学正确性、排期工作量不在本次论证重点，只在与需求发生冲突时提及。

---

## 2. 总体结论

方案的**计算主线是扎实的**：图模型 + 强制约定声明 + 齐次矩阵合成 + 回归基准，这套骨架能把"转换"做对，`T_A_B` 的语义约定写得尤其好，是同类工具最常见的翻车点，方案在源头堵住了。

但从需求看有三个结构性问题，建议在进入开发前解决：

| 序号 | 问题 | 性质 |
|---|---|---|
| **R1** | 痛点 1"无法判断哪个是当前有效值"，数据模型没有支撑（无状态、无来源），单文件不等于单一事实源 | 核心痛点未闭环 |
| **R2** | 场景 B"标定结果与设计值对比"没有对应功能；"复核"被 1.3 节明确排除（环路一致性、对账） | 显性需求落空 |
| **R3** | 方案通篇未提"便携工具箱子软件"的集成约束，选型（PySide6 + PyVista）与现有工程（PyQt5 + matplotlib）冲突 | 集成需求缺位 |

一句话：**转换能做对，复核做不了；账本能记账，但认不出哪笔是"现行账"。**

## 3. 需求追溯

### 3.1 痛点 → 功能覆盖度

| 痛点（1.1） | 承接功能 | 覆盖度 | 说明 |
|---|---|---|---|
| P1 无单一事实源 / 无法判断当前有效值 | A1/A2 YAML 账本 + Git 建议 | **不足** | 账本集中了"所有值"，但数据模型无法区分设计值 / 标定值 / 作废值，两者并存时仍回答不了"哪个有效"。见 R1 |
| P2 无自动计算，人工拼接易错 | B\*、C1~C3、D1 | **充分** | 图 + 求逆 + 合成，闭环完整 |
| P3 无直观呈现 | E1~E8 | **充分** | 但全部 P1，不在最小闭环内，与"一张图"的定位自相矛盾（见 5.2） |
| P4 无误差追踪 | C4、D6 | **不足** | 只做了静态 RSS 合成；"追踪"暗含多状态/时间维度对比，现方案没有。D6 优先级 P1 与核心卖点不符 |
| P5 无集中交付物 | F1~F5 | **充分** | 报告 + CSV 导出闭环完整 |
| **P6 复核麻烦**（用户原话，1.1 未单列） | — | **缺失** | 见 R2。设计值 vs 实测对比、环路闭合、限值判据三项均无功能 |

### 3.2 场景 → 功能追溯

| 场景（3.3） | 用例 | 功能 | 追溯结论 |
|---|---|---|---|
| A 设计阶段录入 | UC-01/02 | A1~A3、B\* | **闭环** |
| B 标定结果核对（与图纸设计值对比） | **无** | **无** | **断链** —— 场景写了，用例和功能都没接住 |
| C 载荷间指向核对（夹角是否符合系统要求） | UC-03/05 | D1/D4 | **半闭环** —— 算得出夹角，但"符合要求"需要期望值/公差比对，无此功能 |
| D 视轴矢量跨系表达 | UC-04 | D2 | **闭环** |
| E 指向精度论证 | UC-06 | D6 | **闭环**，但 D6 被排在 P1 |

场景 B 是设计与验证阶段最高频的复核动作之一（每次标定、每次试验后都要做），却是唯一完全断链的场景。

### 3.3 "不是什么"边界核对

1.3 节排除项中，有两条与用户显性需求冲突：

| 排除项 | 与需求的关系 | 建议 |
|---|---|---|
| 不做环路一致性 | **冲突**。"复核"的核心手段就是环路闭合 `T_A_B · T_B_C · T_C_A ≈ I`。方案 2.1 已有闭合公式，T5 已测逆变换，实现成本约 1 人日 | **收回排除，纳入 P0/P1** |
| 不做对账校验 | **部分冲突**。会计意义上的"对账"可不做；但用户要的"复核"要做，二者不是一回事 | 改写措辞，明确复核功能要做 |
| 不做凭证、经手人、审计日志 | **可接受**。审计确非本阶段 | 保留排除，但需补轻量"来源标注"（≠审计，见 4.1） |
| 不做轨道动力学 / 姿控 / 高精度天文 | **正确** | 保持 |
| 不做热变形模型 | **可接受**，但验证阶段热变形数据要能录进账本（作为多状态值之一） | 归入 R1 的状态机制解决 |

## 4. 关键发现

### 4.1 R1｜"当前有效值"痛点缺少数据模型支撑（高）

痛点 1 的原话是"无法判断哪个是当前有效值"。方案的解法是"集中到一个 YAML"。但集中只解决"散落"，不解决"有效性"——当结构图纸的设计安装矩阵和整星标定的实测安装矩阵都需要留档时，一个 `transform` 节点只有一组 `rotation + translation`，二者无法共存，更无法回答哪个是当前值。

**这是需求与数据模型的直接错配，而且改动成本随开发推进急剧上升，必须在数据模型冻结前决定。**

建议在 `transform` 上补 3 个轻量字段（都不构成审计系统）：

| 字段 | 类型 | 作用 | 成本 |
|---|---|---|---|
| `source` | string | 来源标注：图纸号 / 报告号 / 表号，如 `ST-2026-JG-021 表3` | 0.1 人日 |
| `status` | enum | `design` / `calibrated` / `as_built` / `obsolete` | 0.2 人日 |
| `effective` | string（可选） | 生效说明：批次号、日期、工况（常温/低温） | 0.1 人日 |

配合查询规则：同一 `(from,to)` 允许多条记录，缺省取 `status` 最高优先级（`as_built` > `calibrated` > `design`），并强制在输出中显示"当前值来自哪条记录"。这才真正回答"哪个是当前有效值"。

### 4.2 R2｜"复核"需求被范围排除，且无对比功能（高）

用户原话：**"坐标系的转换、复核都很麻烦"**。复核是与转换并列的显性需求，但方案中：

- 无"设计值 vs 标定值"对比功能（场景 B 断链）；
- 环路一致性被 1.3 节明确排除；
- 无限值/公差比对（场景 C 的"符合系统设计要求"无法判定）。

建议补 3 项复核功能（编号续接现有体系）：

| 编号 | 功能 | 输入 | 输出 | 建议优先级 |
|---|---|---|---|---|
| **G3** | 变换对比 | 两条 transform 记录（如 design vs calibrated） | ΔR（等效转角，角秒）、Δt（mm）、是否超限 | **P0** |
| **G4** | 环路闭合检查 | 账本图 | 每条基本回路的 `T_loop` 与单位阵偏差，列出超差回路 | **P0** |
| **G5** | 限值登记与符合性检查 | 期望值 ± 公差（如两载荷光轴夹角 30°±0.1°） | 计算值、偏差、通过/不通过 | P1 |

其中 G4 成本极低（图 + 矩阵乘法都已存在，只差一个回路枚举与偏差输出），却是"复核"场景下性价比最高的一项。G3 直接承接场景 B。

### 4.3 R3｜便携工具箱集成需求完全缺位（高）

方案按独立软件设计（PySide6 GUI、PyVista 3D、PyInstaller 单文件），但目标是**便携工具箱中的子软件**。对照现有工程（`radar_tool/`），存在以下冲突与缺位：

| 项 | 方案 | 工具箱现状 | 结论 |
|---|---|---|---|
| GUI 框架 | PySide6 | **PyQt5**（`main_window.py` + `*_panel.py`） | **冲突**。同一进程混用 PyQt5/PySide6 会与 Qt 绑定冲突，必须二选一 |
| 3D 渲染 | PyVista + pyvistaqt | matplotlib | PyVista 依赖 VTK，打包体积增加 100MB+，与"便携"定位冲突 |
| 模块形态 | 独立程序 `cledger gui` | `QTabWidget` 懒加载面板（`VisualizationPanel`、`CalibrationPanel`…） | 应改为 `CoordinateLedgerPanel` 挂载到现有标签页体系 |
| 报告导出 | Jinja2 + Markdown | 已有 `experiment_word_export.py`（Word）、`export_safety.py`（覆盖确认） | 应复用，而非另起炉灶 |
| 参数批次管理 | 无 | 已有 `calibration_batch_store.py`（批次参数保存/复用） | 状态/版本机制可借鉴此模式 |
| 邻接数据 | 无 | 测向校正模块已存 3×3 变换矩阵于批次配置 | 需明确是否互通，避免两套矩阵管理 |
| 设计文档 | 无归档约定 | `docs/设计文档/` 按模块一文件 | 本文档即按此约定归档 |
| 打包 | PyInstaller 单文件 | `PACKAGING_GUIDE.md` 既有约定 | 需给体积预算上限 |

建议在方案中新增"第 9.5 节 / 便携工具箱集成约束"，至少回答 8 个问题（见 6.2 集成需求 I1~I8）。

### 4.4 优先级与价值主张不一致（中）

方案 1.2 的一句话定位含 6 项能力，但最小闭环（P1+P2，10.3 节）**砍掉了其中 2 项半**：

| 定位能力 | 功能编号 | 当前优先级 | 是否在最小闭环 | 问题 |
|---|---|---|---|---|
| 集中记录 | A\* | P0 | 是 | — |
| 自动计算 | C\*/D1 | P0 | 是 | — |
| 矢量跨系表达 | D2 | P0 | 是 | — |
| **载荷指向计算** | D4 | **P1** | **否** | 定位里的核心能力被降级 |
| **误差预算** | D6 | **P1** | **否** | 同上，且直接对应痛点 P4 |
| **3D 可视化** | E\* | **P1** | **否** | "一张图"完全不在最小闭环 |
| 报告导出 | F\* | P0 | 是 | — |

若 2 周最小闭环交付后拿给设计师用，得到的是"一个能算矩阵的 CLI"，与"一份账本 + 一个计算器 + 一张图 + 一份报告"的承诺差距明显。要么调整定位措辞，要么把 D6（误差预算）提到 P0——它是痛点 P4 的唯一承接者，且输出"星敏 2.1″ + 相机 3.2″ → 3.83″"这类结论正是评审要的东西。

### 4.5 约定清单有遗漏（中）

2.2 节"必须显式声明"机制是方案最大亮点，但清单本身漏了两项高频踩坑约定：

| 遗漏项 | 风险 | 建议 |
|---|---|---|
| **欧拉角内旋 / 外旋** | ZYX 内旋与外旋结果不同，附录 15.1 提了"内旋"，但 2.2 强制声明表里没有 | 加入必填项，缺省报错 |
| **坐标系物理定义**（各轴指向的文字语义） | `axis: Z_FORWARD` 只说了 Z 轴，X/Y 物理意义（如 X 沿飞行方向）无法在评审中引用 | `frame` 增加 `definition` 文本字段 |

另建议显式声明两条假设（现方案默认成立但未写出）：

- `sigma.t` / `sigma.r_arcsec` 按**各向同性**处理；真实安装误差是 3×3 协方差，M1 简化可接受，但应在文档写明假设，并为协方差扩展留字段位；
- 平移误差与旋转误差**相互独立**，RSS 叠加成立的前提是独立性，热变形等共因项不在 M1 范围。

### 4.6 两条技术-需求冲突（中低）

| 冲突 | 说明 | 建议 |
|---|---|---|
| A2"写出保留注释与格式" vs 技术选型 PyYAML | **PyYAML 不保留注释**，写出必然丢注释。这是硬冲突，不是配置问题 | 改用 `ruamel.yaml`，或将 A2 需求降级为"不保证注释保留"，二选一 |
| NFR"单次查询 < 1 ms" | 对交互式设计工具无意义（<100 ms 无感），属过度规格；而包体积、离线运行、数据文件保密要求等真正影响"便携"的 NFR 缺失 | 删 1 ms 指标；补 4 条 NFR（见 6.3） |

### 4.7 其他观察（低，记录备查）

- **魔法数字痛点没有闭环**：1.1 节点名"算法代码中的变换公式与魔法数字"是痛点来源，但交付物只有 CSV 矩阵表，程序员仍需手工搬运进代码。建议补 **G6 代码片段导出**（C 头文件 / Python dict / MATLAB 常量），直接消灭魔法数字。成本约 1 人日，收益直接。
- **录账效率**：CAD 装配体常一次导出几十个安装矩阵，逐条手录 YAML 易错。建议补 **G7 Excel/CSV 批量导入 transform**。
- **误差预算示例表**（6.4 D6）中"star_tracker_1 → body（基准）"一行语义不清，body 是基准为何还占一段；建议示例改为真正的两跳路径（如 body → st1 → camera）。
- 多文件合并（A4）排 P1 合理；若按分系统各管各的账本，合并加载是常态需求，不是边角功能，可考虑提前。

## 5. 需求补充与优先级建议

### 5.1 建议新增需求项（编号续接现有体系）

| 编号 | 名称 | 承接 | 建议优先级 | 工作量 |
|---|---|---|---|---|
| G1 | `transform.source` 来源标注 | R1 / 痛点 P1 | **P0** | 0.1 |
| G2 | `transform.status` 状态 + 多值共存与缺省选取规则 | R1 / 痛点 P1 / 场景 B | **P0** | 0.5 |
| G3 | 变换对比（ΔR/Δt + 超限判定） | R2 / 场景 B | **P0** | 1.0 |
| G4 | 环路闭合检查 | R2 / 用户"复核"原话 | **P0** | 1.0 |
| G5 | 限值登记与符合性检查 | 场景 C | P1 | 1.0 |
| G6 | 代码片段导出（C/Python/MATLAB） | 痛点"魔法数字" | P1 | 1.0 |
| G7 | Excel/CSV 批量导入 transform | 录账效率 | P1 | 1.0 |
| G8 | `frame.definition` 轴向物理定义文本 | 评审可引用性 | P1 | 0.2 |
| G9 | 多账本 diff（基线 vs 当前） | 回归 / 评审 | P2 | 1.5 |
| I1~I8 | 便携工具箱集成约束（见 6.2） | R3 | **P0（决策项）** | 决策成本 |

> G1~G4 合计约 2.6 人日，恰好补上"复核"与"当前有效值"两个核心缺口，性价比显著高于现方案中若干 P1 项。

### 5.2 最小闭环重定义建议

现方案：`P1 + P2` = 读账 + 算账 + 出数（2 周）。

按需求价值重排后建议：

| 层级 | 内容 | 周期 |
|---|---|---|
| **MVP（必达）** | 账本读写 + 校验、两系变换查询、矢量跨系、误差预算（D6 提前）、矩阵导出、**变换对比（G3）**、**环路检查（G4）**、**来源/状态字段（G1/G2）** | 2 周 |
| **第二批** | 3D 静态图（matplotlib，非 PyVista）、指向计算（D4）、报告导出（复用 Word 导出）、限值检查（G5） | +1 周 |
| **第三批** | 交互式 3D（视选型结论）、代码导出（G6）、批量导入（G7）、多账本 diff（G9） | +1 周 |

理由：设计师的高频动作排序是**查变换 > 录账 > 复核对比 > 误差预算 > 出报告 > 3D 核对**。3D 是"看得见"的加分项，不是"算得对、复核得了"的必选项；而复核（G3/G4）必须进 MVP，否则工具解决不了用户原话里的半个痛点。

## 8. 结论

方案的**计算内核需求覆盖充分，方向正确**；但作为面向"设计与验证阶段"的坐标系管理工具，**"复核"和"当前有效值"两条核心需求没有闭环**，且**与便携工具箱的集成约束整体缺位**。

建议按以下顺序修订方案至 v1.1：

1. **冻结数据模型**：补 `source` / `status`（Q2 决策，最高优先级，改动成本随时间上升）；
2. **收回范围排除**：环路一致性、变换对比纳入功能集（G3/G4 进 MVP）；
3. **明确集成约束**：GUI 框架二选一（I2），面板形态、体积预算、复用边界写清；
4. **重排最小闭环**：D6 误差预算 + G3/G4 复核进 MVP，3D 后置；
5. **补齐约定与假设**：内旋/外旋必填、`frame.definition`、误差模型假设显式化；
6. **处理技术冲突**：A2 注释保留改 `ruamel.yaml` 或降级需求；删除 1 ms 指标。

完成上述 6 项后，方案即可支撑进入开发。其中第 1、2、3 项为阻塞项，建议本周内决策。
